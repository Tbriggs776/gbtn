# gbtn

One Next.js 15 App Router app behind Growth by the Numbers — the fractional-CFO practice of Tyler M Briggs Inc dba GBTN. Three products share the tree: the public marketing site (`app/(marketing)`), a multi-tenant authenticated client portal (`app/portal`), and GBTN's own internal agency CRM (`app/portal/crm`, staff only — its data is GBTN's business, not a client's). The active workstream is a per-client QuickBooks Online integration being prepared for the Intuit App Store.

## There is no local or staging database — dev *is* production

`.env.local` points `NEXT_PUBLIC_SUPABASE_URL` at the same Supabase project as production (`yvzrtwswvdlxwtqetiqs`) and holds the production service-role key. `npm run dev`, every server action you fire, every cron route you curl and every `scripts/*.mjs` you run reads and writes real client books. There are no tests anywhere either, so `npx tsc --noEmit` plus reading the code is the whole verification story — **never validate a write path by triggering it.** Reason it through, then hand the user the exact command or click-path and let them decide.

`.env.local` holds only six vars (the three Supabase ones, `NEXT_PUBLIC_SITE_URL`, `RESEND_API_KEY`, `EMAIL_FROM`) — no `QBO_*`, no `CRON_SECRET`, no `UNSUBSCRIBE_SECRET`. Every QBO path is therefore inert locally; that is missing config, not a bug to chase.

- Never run `npm run lint`. It maps to `next lint`, but eslint is absent from package.json, package-lock.json and node_modules and there is no eslint config, so it blocks on Next's interactive installer.
- On a fresh clone run `npm install` and one `npm run dev`/`npm run build` **before** `npx tsc --noEmit` — tsconfig `include`s `next-env.d.ts` and `.next/types/**`, neither of which is committed. Keep `tsconfig.tsbuildinfo`: with `incremental: true` a warm check is ~12s against ~60s+ for a cold full one on this OneDrive checkout.
- `npm audit` shows 5 findings (4 high, 1 critical). Expected noise. `npm audit fix --force` breaks the exact `next` pin 15.5.19 and still cannot fix xlsx.
- Migrations: `node scripts/migrate.mjs supabase/migrations/0027_app_config.sql`. The path must be repo-relative; an absolute Windows path ENOENTs. It runs the whole file as one un-transacted `client.query()` against production and there is no migration ledger, so production is the only record of what is applied. Confirm with the user before every invocation.
- `scripts/` holds exactly one reusable tool — `migrate.mjs`. Everything else is a one-off that opens a production service-role client from `.env.local` and defaults to a hardcoded, now-stale `C:/Users/Tyler/...` path: `load-floor-daddy-orders.mjs`, `refresh-floor-daddy-financials-qbo.mjs` and `load-floor-daddy-financials*.mjs` **delete before inserting**; `provision-floor-daddy.mjs` creates a client row and uploads files; `seed.mjs` creates an admin auth user. Several are pre-approved in `.claude/settings.local.json` and run with no prompt. Never invoke one to "refresh" data.
- Cron routes can be curled locally, but they hit production and several are irreversible: `/api/cron/crm-engine` advances drips, fires scheduled blasts and sends task reminders through Resend and Twilio to **real contacts**; `/api/cron/qbo-sync` clean-reloads financials. `CRON_SECRET` is not in `.env.local`, so `curl -H "Authorization: Bearer $CRON_SECRET" ...` 401s by default — a safety feature, not a setup gap.

## Auth and permissions — this is the security model

- Two strict login doors: `/login` for clients (lands on `/portal`), `/team` for staff (lands on `/portal/crm`). One shared `LoginForm` takes an `audience` prop and signs the wrong role back out. Auth changes touch both.
- Two independent role axes. `profiles.role` is the platform role (`admin` = GBTN staff, `employee` = CRM-only staff, `client`). `memberships.role` is per client (`admin | finance | ops | marketing`) — one person can be finance at one company and ops at another, so `session.roles[clientId]` is always the lookup. Capabilities: `financials | marketing | ops | documents | manage_users`.
- `lib/permissions.ts` is the one matrix, mirrored by the SQL helpers in `0014_client_roles.sql` (`can_read_financials`, `can_read_marketing`, `can_read_ops`, `is_client_admin`, `is_staff`). Change both, plus `NAV_CAPABILITY` and the page's `requireCapability`, together.
- **RLS is defense-in-depth, not the gate.** Dashboards read through the service role, which bypasses RLS. The `requireCapability`/`assertCapability` call at the top of the page or handler is the boundary. Gate first, fetch second — a page that fetches before gating is a real cross-tenant leak.
- Three Supabase clients, two of them exporting the same name. `createClient()` from `@/lib/supabase/server` (async, cookie-bound, RLS-enforcing) is the default for server components, actions and route handlers. `createClient()` from `@/lib/supabase/client` is browser-only — imported on the server it compiles, runs, and silently returns empty rows, which reads as a data bug. `createAdminClient()` from `@/lib/supabase/admin` bypasses RLS entirely; reach for it only behind an `assert*`/`require*` gate.
- `require*` redirects (pages, layouts); `assert*` throws (server actions, route handlers). A `require*` in a route handler returns an HTML redirect where the caller expects JSON.
- `middleware.ts` imports nothing but `next/server`, matches only `/portal/:path*`, and does nothing but sniff for a cookie named `sb-*-auth-token`. Anything transitively reaching `@supabase/*` breaks the Edge deploy. Layouts never run for route handlers, so a new `route.ts` has no real gate until you call one inside it: under `app/portal/` middleware checks only that a cookie exists (no role, no client scope), and under `app/api/` nothing runs at all.
- `getActiveClient()` silently falls back to `clients[0]` when `?client=` names a client the user cannot access. Never infer the rendered client from the URL. `ClientSwitcher` pushes `pathname + "?client=" + id`, dropping every other query param (e.g. `?window=` on google-ads).
- Two deliberate exceptions: `app/portal/page.tsx` has no page-level guard and gates each financial block inline with `sessionCan()`; `app/portal/admin/page.tsx` uses `requireSession()` and then narrows the service-role `listUsers()` inline to the clients where this session is admin (`admin/actions.ts` does the same scoping via `manageableClientIds()`). Email/password changes go through the stricter `assertCanChangeCredentials()`.
- `/portal/crm/*` is gated exactly once, in `app/portal/crm/layout.tsx` via `requireStaff()`; only `crm/settings` adds `requireAdmin`. Every CRM server action re-asserts with `assertStaff()`.
- `profiles.role` is protected by the `guard_profile_role()` BEFORE-UPDATE trigger (0022), not by RLS — role changes must use the service-role client, and the failure reads like an application error, not an RLS denial.

## Where things live

- Portal server actions live in the route segment (`app/portal/<section>/actions.ts`) and are imported into `components/portal/**` via `@/app/...`. That direction is intentional; do not "fix" it. They return `{ ok?, error?, message? }` rather than throwing — keep that contract for `useActionState` consumers.
- CRM is layered differently. Its server actions (`lib/crm/actions.ts`, `ai-actions.ts`, `campaign-actions.ts`, `import-actions.ts`, `settings-actions.ts`) take domain inputs, call `assertStaff()` and then build their own RLS-bound `createClient()`, and return the discriminated `ActionResult` from `lib/crm/types.ts` (`{ok:true,data?} | {ok:false,error}` — no `message`). Underneath, the data layer (`service.ts`, `comms.ts`, `campaign-engine.ts`) takes an injected `db: SupabaseClient` first arg so both the action path and the service-role cron path can drive it. `lib/{ops,marketing,google-ads}/service.ts` instead build the admin client internally and assume the caller already checked.
- `import "server-only"` marks modules touching the service role, Vault or a vendor secret (36 of 74 lib files). Six are deliberately NOT server-only because `"use client"` components import them: `lib/permissions.ts`, `lib/format.ts`, `lib/financials/metrics.ts`, `lib/financials/analysis.ts`, `lib/ops/pipeline.ts`, `lib/pricing/engine.ts`. Adding the import breaks the build.
- Tailwind v4, no `tailwind.config.*` anywhere. Tokens live in the `@theme` block of `app/globals.css`, brand helpers in `@utility`. `--font-sans` is Spectral, a **serif**, and legacy names are remapped (`teal-500`/`cyan-500` render crimson). Creating a tailwind config file is inert.
- No `loading.tsx`, `error.tsx`, `not-found.tsx` or `next/dynamic` anywhere, so an uncaught throw blanks the page.
- File uploads: the browser writes directly to the private `client-files` bucket at `${clientId}/...`, then a server action records the row and re-checks the prefix (that prefix check is authorization, not cosmetics). Downloads use 60-second signed URLs.
- **Four hardcoded floor-daddy gates, and they are asymmetric.** `components/portal/portal-nav.tsx:75` shows the Ops Reports / Operational Levers / Pricing nav entries on `activeClient?.slug === "floor-daddy"`; `app/portal/pricing/page.tsx:11` and `app/portal/operational-levers/page.tsx:11` each redirect unless the slug is in their own `ENABLED_SLUGS`; `/api/pricing/catalog` gates on the literal UUID `1c33f100-30eb-4337-b923-a48f84ba6e95`. Ops Reports has no page-level gate, so a nav-only edit half-works — Ops Reports opens and the other two bounce. Onboarding a second client means all four.

## Secrets — three tiers, not interchangeable

1. **Env vars**: Supabase keys, Resend, the five `QBO_*`, `CRON_SECRET`, `UNSUBSCRIBE_SECRET`, `NEXT_PUBLIC_*`.
2. **Supabase Vault, platform-wide** (`store_/read_platform_secret`): the Anthropic key, Twilio, CallRail — entered through the app UI (Admin → Integrations, CRM → Settings). Adding `TWILIO_AUTH_TOKEN` to env creates a second source of truth the code never reads.
3. **Supabase Vault, per client** (`store_/read_connection_secret`, keyed on `marketing_connections.id`): marketing/GHL tokens.

QBO OAuth tokens are the exception to both Vault patterns — AES-256-GCM ciphertext in ordinary columns. `.env.example` sets only 6 vars (plus 2 commented-out optionals) of the ~27 `process.env.` names across `app/`, `lib/` and `scripts/`, and omits every `QBO_*`; a grep of `process.env.` plus SETUP.md is the real inventory. `UNSUBSCRIBE_SECRET` falls back to `CRON_SECRET`, and in production `sendContactEmail` refuses to send with neither set.

## Integrations

- **QuickBooks is read-only, as a product invariant** asserted in the code, the App Store listing copy, the privacy policy and the Intuit security questionnaire. Never create/update/void/delete, and never touch the Invoice or Payment `/send` endpoints — they email the client's customers. Propose; the human posts.
- `QBO_MINOR_VERSION` is a source constant (`lib/financials/qbo/config.ts:42`), not an env var; `client.ts` stamps it on every request as `minorversion=75`. Do not bump it without re-verifying against `docs/qbo-api/`.
- `QBO_TOKEN_ENC_KEY` is dual-purpose: token encryption **and** the OAuth `state` HMAC. It must decode to exactly 32 bytes (64 hex chars or base64) or every QBO call throws, and rotating it orphans every stored connection and every in-flight authorization at once. Generate one with `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`.
- QBO refresh tokens **rotate** — any path calling `refreshTokens()` must persist the new one. Go through `getValidAccessToken()`. `QBO_ENVIRONMENT` defaults to `"sandbox"` and the other QBO vars to `""`, so a misconfigured deploy quietly reads fake data instead of failing.
- `/api/qbo/connect` serves two flows off one URL: with `?client=<id>` it is the staff flow (session + `financials`); with no param it is the public Intuit App Store flow, and its callback legitimately auto-provisions a `clients` row with `status='prospect'`. `/api/qbo/disconnect/intuit` still trusts a bare realmId — treat it as an unauthenticated mutation until the signed-payload TODO lands.
- `loadMrpResult` (`lib/financials/qbo/mrp-sync.ts`) is a clean reload: it deletes every matching `financial_uploads` row and its `financial_line_items` before inserting. `/api/cron/qbo-sync` runs it **unattended at 06:00 for the current year, for every active connection** — so a hand-fixed line item, or a month-end-close Step 10 load, is gone by morning. The only durable correction is a `category_mappings` row (`raw_label_norm` + `category` + `statement_type`), which the sync reads back and lets win.
- `loadOrders` (`lib/ops/service.ts`) likewise **deletes** a client's `ops_order_lines` before inserting, because an RFMS export is a full snapshot. Do not convert it to an upsert — that leaves deleted-in-RFMS lines as permanent ghosts.
- Twilio, Resend and CallRail are hand-rolled fetch wrappers (only `@anthropic-ai/sdk` is a vendor SDK). Twilio's HMAC-SHA1 signature covers the full URL rebuilt from `x-forwarded-proto`/`x-forwarded-host`, so changing the hostname, adding a proxy, or appending a query param 403s every webhook with no other symptom — and the `fullUrl()` helper is copy-pasted in all three `app/api/twilio/*` routes.
- Two independent CallRail clients: `lib/marketing/callrail.ts` (per-client vaulted key → `marketing_metrics_daily`) and `lib/crm/callrail.ts` (GBTN's own platform account → `crm_activities`). Never cross them.
- Anthropic is pinned to `claude-opus-5` with no `temperature` and no `budget_tokens` (both 400 on opus-5); callers degrade silently on `{ ok:false, reason:'no_key' }`.
- Crons have **two drivers**: the five entries in `vercel.json` and Supabase pg_cron calling the same routes with a DB-held secret at `app_config('cron_secret')` (`lib/cron-auth.ts`). Rotating one secret does not disable the other, and retiring a route requires unscheduling the pg_cron job by hand. Adding a cron means both the `route.ts` and the `vercel.json` entry; keep `"framework": "nextjs"` there, since the Vercel dashboard has framework set to null.
  - Exception: the two uncommitted QBO crons (`qbo-sync`, `close-monitor`) do **not** call `authorizeCron` — they compare `process.env.CRON_SECRET` directly and 503 when it is unset, so pg_cron's DB-held secret cannot drive them. Port them when that workstream lands.
  - Verified 2026-09-14 by a SELECT-only query over `cron.job`: pg_cron holds exactly three jobs, all active and all routed through `public.run_cron_endpoint(...)` — `callrail-sync` (`0 9 * * *`), `crm-engine` (`*/5 * * * *`) and `marketing-sync` (`0 8 * * *`), one per committed `route.ts` under `app/api/cron/`. The untracked `qbo-sync` and `close-monitor` routes are scheduled only in `vercel.json`, not in pg_cron. The GoHighLevel jobs that outlived commit 6569616's removal of the sync (`ghl-backfill`, `ghl-sync`, `ghl-daily-review`) have since been unscheduled. The `ghl_*` tables from 0021/0028 and the stored per-client GHL tokens are deliberately left in place; do not drop them as cleanup.
- Do not remove `experimental.serverActions.bodySizeLimit: "25mb"` from `next.config.mjs`, and do not expect it to fix uploads on Vercel — the platform 413s bodies over ~4.5 MB at the edge before the function runs. Large uploads go through a route handler with client-side gzip (`x-gbtn-encoding: gzip`, hard 4,000,000-byte cap), as `app/api/ops/import/route.ts` does.

## Financial math invariants

- Signed convention: expenses and liabilities positive, credits negative. **Never `abs()` a value that flows into a total, a subtotal or a balance** — it silently corrupts EBITDA and the balance sheet. `Math.abs` for ranking by magnitude or for display formatting is fine and already used (`lib/financials/fpa.ts:208`, `metrics.ts:173`).
- Use QBO `Balance` (still owed), never `TotalAmt`, for aging and cash projection — and `Balance` is calculated and generally not filterable in the query language, so filter client-side or use the aging reports. Voided records persist with `Balance: 0` and must be excluded.
- Parse QBO reports with the one recursive parser in `lib/financials/qbo/report-parser.ts`, keyed on the stable `group` field and column position — never on display labels (localized, space-padded). Money cells are strings; `""` means no value.
- QBO's `CashFlow` report is historical GAAP, not the 13-week projection. The forward view is built in-house from open Bills/Invoices, bank balances, payroll and recurring items; opening cash is the BalanceSheet section with `group: "BankAccounts"`.
- Negatives in AR/AP aging are unapplied credits, not debts. A party with large offsetting buckets means the aging is distorted — do not act on it until credits are applied.

## Migrations

Filenames are `NNNN_snake_case.sql` and **numbers collide** — two `0018_`, two `0020_`, four `0021_`, two `0022_`. Highest prefix is 0028, so a new file is 0029+; list the directory first. Apply order is filename order, not number order, and it is not dependency order: a fresh rebuild fails at `0010_google_ads.sql`, which uses `can_read_marketing()` first defined in `0014_client_roles.sql`. Write everything idempotently (`create ... if not exists`, `drop policy if exists`) because re-running is the normal recovery path. Tightening a policy means dropping the old policy **name** — Postgres ORs permissive policies, and this bug already shipped once (0014 → 0015). Never add client INSERT/UPDATE/DELETE policies to the data tables; their absence is the design, and all writes go through the service role.

## Commit style

House format is `<Area>: <what changed>` in sentence case — **not** Conventional Commits (56 of the last 80 subjects; exactly one `docs:` in 120). Areas are product surfaces: Ops Reports, Pricing, CRM, Portal, Admin, Auth, Cron, Financials, FP&A, Floor Daddy, Marketing, Security, and GHL (historical only — the sync was removed in 6569616). `Fix: ` is capitalized like an area, not a type. Real subjects:

- `GHL client: bound every request with a 30s timeout (hangs stalled the sync) (#26)`
- `Fix: GHL sync crash — recomputeAggregates must UPDATE, not upsert`
- `Ops Reports: stamp the import date in Arizona, not UTC`

Subjects are long on purpose — median 62 chars, max 84, 17 of 80 over 72. Do not trim to the 50/72 rule. Every recent commit has a body: a root-cause narrative hard-wrapped at ~80 columns saying what was broken, why, what the fix does, and what you deliberately left alone. End with `Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>`. **Never hand-write a `(#N)` suffix** — GitHub's squash-merge adds it. Type/scope information lives in the branch name instead (`feat/ghl-30d-chunked`, `fix/ghl-aggregates`, `chore/ghl-90day`).

## Git and data hazards

- **Never `git add -A` or `git add .`.** Many untracked paths sit in the tree — `docs/`, root scratch files `_join.mjs` and `Refresh Marketing Metrics.cmd`, and more. Stage explicit paths only. The four credential-bearing paths (`google-apps-script/`, `.claude/settings.local.json`, `.claude/skills/month-end-close/clients/*.md`, `scripts/marketing-secrets.ps1`) are now gitignored, but that is a safety net, not a licence to bulk-add.
- **`.claude/settings.local.json` itself contains live GoHighLevel and CallRail credentials in plaintext**, baked into pre-approved command strings in its `permissions.allow` list. It can never be committed or pasted anywhere — including when someone reasonably asks you to "commit the .claude directory so the skills are shared."
- **Never restore or revert `.gitignore`.** The block ignoring `floor-daddy-contacts.xlsx` (33.7 MB), `floor-daddy-callrail-calls.xlsx` (16.9 MB), `Floor Daddy - Marketing Metrics.xlsm` and `scripts/marketing-secrets.ps1` is an uncommitted working-tree change. Reverting it re-arms a ~52 MB client-PII + live-credentials commit.
- **Client close profiles never enter git.** `.claude/skills/month-end-close/clients/*.md` hold live client financials — QBO realm ids, bank balances, named vendors, member draws — and this repo is PUBLIC. They are gitignored (`_TEMPLATE.md` is the deliberate exception) and reach other machines via OneDrive sync, not version control. Never un-ignore one, and never quote its figures into a tracked file, a commit message or a PR.
- Git history does not reflect the working tree: the whole QBO/Google-Ads workstream is uncommitted. Two **tracked** files carry uncommitted edits with no backup — `.gitignore` and `app/portal/financials/page.tsx` (the QBO/cash-flow wiring) — so `git restore .`, `git checkout -- .` and `git stash` are all destructive here. Run `git status` for the current list (longer than any list in this file) and treat everything it reports as untouchable. `vercel.json` already schedules two crons whose routes are not on deployed main.
